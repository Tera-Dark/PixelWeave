# PixelWeave 性能专项优化与防单页过载策略

版本：v0.8 性能专项补丁 · 2026-10-25

## 目标

**不是单纯压缩 CSS 数字，而是让只浏览画廊的访问者不承担整个像素动画编辑器的 CPU/DOM 成本。**

当前保留单仓库、纯静态 Github Pages 结构；按功能生命周期隔离工作量，并给静态资源和浏览器交互设置 CI 门禁。

## 本次已经实施

### 1. 当前页面才运行当前动画

- src/main.js：浏览器标签页 document.hidden 时停止帧绘制，页面重新可见后不批量追赶隐藏期间的帧。
- Gallery / Studio 互斥；Studio 激活时不再循环重绘隐藏画廊的 Hero/作品 Canvas。
- Gallery 激活时不再更新隐藏编辑器；Gallery 内的 Canvas 进入视口才有动画工作量（IntersectionObserver，支持没有该 API 的回退）。
- 复杂斜向图层展开沿用既有离屏守卫，不因为主帧播放而在视口外反复刷新。

### 2. Studio 延迟初始化

- 初次打开 Gallery 只加载首页必需的药瓶模型与作品信息。
- 132 个 Cel 网格单元、图层管理面板、调色板等结构仅在首次进入 Studio 时创建；再次进出不会重建。
- 私人存档仍先 restore 到内存。延迟初始化只改变**显示控件创建时机**，不会删除本地编辑工程或禁用导出。
- 可选 local LLM 状态探测直到用户打开 LLM 创作抽屉才发起请求，防止公开 Pages 首页不必要的 /api/status 请求。

### 3. 参考动画库按视口取图

- 左栏每个条目 Canvas 自身创建成本很低，但远离可视区域的外部精灵图不应在页面一开就下载。
- 缩略图使用 IntersectionObserver 按需触发。切换当前作品仅更新选中状态，不再整体重建素材列表。
- Promise 图片缓存是有上限的 LRU（12 个 URL），避免将来素材达到 100+ 后浏览器长期持有全部原始源图。
- 在后台标签页或参考播放器离开视口时暂停动画推进，不在回到页面时追赶所有错过的帧。
- 外部作者图片保持外链与许可约束，不后台爬取、采样训练或加进正式原创资产库。

### 4. 样式依赖瘦身

- 新增 src/site-base.css（不到 1 KB 的基础排版、变量和表单键盘可达性定义）。
- Atlas 删除对 src/style.css 和 src/pixel-ui.css 的依赖，减少约 58 KB 原始 CSS 请求量。
- Lab 不再加载整套 src/pixel-ui.css，减少约 31 KB 原始 CSS 请求量。
- 删去 CSS 的 Google Fonts @import：所有页面使用非阻塞可选字体 link，首屏允许系统字体回退。
- 首页 Collection、次要说明区域和工作站重型图层展开采用 CSS content-visibility:auto + contain-intrinsic-size，缩短离屏布局/绘制的同步工作。

**注意：**以上 KB 估算指 GitHub 原始源码字节大小，不是实际网络传输量，不能当作实际首屏加载耗时。浏览器网络条件、缓存、字体和外部图片都会影响最终体验。

## 强制性能门禁

- tests/performance-budget.test.mjs：扫描 HTML 实际同步 CSS 和 JS import graph，限制三个页面的源码体积预算：主站 220 KiB；Atlas 85 KiB；Lab 80 KiB。
- 同一个测试还保护按视口加载图片、有上限缓存、隐藏动画不渲染、可选模型探测延后触发及第三方字体不阻塞 CSS。
- tests/e2e/performance.mjs：真实 Chromium 比对 Gallery→Studio→Gallery 的 Canvas 绘画计数，确认隐藏页面不在每帧画图；确认 Gallery 首次没有完整 Cel 网格；Studio 第一次进入才有 132 个 Cel；LLM 状态请求只发生在展开助手之后；参考库正常列出已审核研究素材。
- 之前的 v0.8 真实编辑器操作测试和四路由导航 E2E 继续保留，所有测试成功后才能部署 GH Pages。

## 继续迭代时不要破坏的约束

1. 非当前页面不得继续启动动画、重复监听外部来源或创建大型 Canvas。
2. 长素材目录不得默认解码全部远端原图；优先可视区加载并设置可证实的缓存上限。
3. 与首屏无关的 API、数据分析、复杂图层操作必须等用户进入对应工作流再启动。
4. 给新页面增加 CSS 时，不能不经预算审查就复用完整编辑器 CSS。
5. 不得通过降分辨率、模糊插值或预渲染截图伪装成性能优化；图层数据应保持真实可编辑。
6. 不能宣称整体“提速 60%”之类数字，除非以后加入有前后对比、网络环境明确的自动化实际计时。

## 当前未解决的进一步机会

- 将主站导入的完整渲染引擎进一步按路由拆分为按需的 ES Module（需要彻底梳理跨模块状态和初始化依赖，目前仅实现视图/控件延迟初始化）。
- 用 IndexedDB 存储大型个人项目而非无限扩大 localStorage JSON；需要迁移、事务与导入导出的安全验证。
- 大规模参考库（1000+ 条）才考虑列表虚拟化和分页，现有 7 条不值得付出虚拟列表复杂度。
- 建立带固定网络节流、冷热缓存两种模式的 Lighthouse/Web Vitals 基准，报告 p50/p95，分清静态文件与第三方外链延迟。

本次没有生成图片、裁切已有图片、修改药瓶素材或把第三方参考作为训练数据。
